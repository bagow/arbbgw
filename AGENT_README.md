# AGENT README: Crypto Arbitrage System Architecture (HFT Edition)

Этот файл предназначен для ИИ-агентов (и разработчиков), чтобы быстро понять актуальную архитектуру проекта, разделение ответственности и потоки данных.

Система была полностью переработана для достижения минимальных (Zero-Latency) сетевых задержек, безопасности ключей и поддержки одновременной мульти-профильной торговли.

Система разделена на две основные части: **Cloudflare (Frontend + Edge Security)** и **VPS (Высокочастотный торговый движок + API-сервер)**.

## 1. Cloudflare (`arb.bagow.com`)

Cloudflare выступает в роли публичного интерфейса, балансировщика и слоя безопасности. **Больше нет прямого HTTP-проксирования по IP** или использования базы D1.

- **Frontend (`/public`)**: Статические файлы интерфейса (HTML/JS/CSS). Хостится целиком на Cloudflare Pages/Workers Assets.
  Фронтенд разделен на:
  - **Scanner (`chart.html`)**: Аналитическая таблица спредов в реальном времени с графиками OHLC.
  - **Trading Dashboard (`index.html`)**: Основной торговый интерфейс с поддержкой профилей (Paper/Real).
- **Worker (`/src/index.js`)**: Выполняет аутентификацию (Basic Auth) и проксирует `/api/*` запросы на домен `api.arb.bagow.com` (который терминируется на сервере VPS через Cloudflare Tunnel), полностью скрывая реальный IP-адрес сервера от возможных DDoS-атак.

## 3. VPS (Швейцария): Zero-Latency Торговый движок и API

Основная торговая логика была переработана: старые компоненты (`rust-collector`, `real-trader`, `paper-trader`) объединены в один высокочастотный **Single-Process Бинарник (`core-node`)**. Это устранило 2-5 миллисекундные задержки на HTTP-запросах и сериализации/десериализации JSON между старыми микросервисами.

На сервере через `systemd` работают следующие основные сервисы:

### A) `core-node` (Порт 3003 - Healthcheck)
Единый CEX-движок арбитража. 
- **Модуль `collector`**: Индивидуальные WebSocket-соединения к биржам (Gate, HTX, KuCoin, Binance, Bybit, Mexc, OKX, Bitget).
- **In-Memory Архитектура (`Arc<DashMap>` + `Notify`)**: Коллекторы кладут новые цены (OrderBook/Tickers) в общую оперативную память. Никакого расхода времени на TCP - движок получает сигналы за наносекунды.
- **Модули `engine::paper` и `engine::real`**: В бесконечном цикле (на каждый "тик" цены) `core-node` перебирает ВСЕ активные торговые профили (paper и real). Для каждого профиля с его личными настройками вычисляются спреды и немедленно принимаются решения.
- Оптимизации для Real-Trader: использование `tokio::join!` для конкурентного старта обеих "ног", защита от частичного исполнения ордеров (Partial Fills), защита через Rate Limiters, и автоматический `Leg Risk Fallback` (если одна нога отвалилась - закрыть позицию маркетом).

### B) `vps-api` (Порт 4000)
Бэкенд инфраструктуры для UI.
- Слушает трафик из Cloudflare Tunnel (`localhost:4000`).
- Отвечает за коммуникацию с Фронтендом: отдает настройки, статистику, стейт профилей и инициирует запросы на UI обновления.

### C) `cloudflared.service`
Оба сервиса `core-node` и `vps-api` скрыты от внешнего интернета. Наружу торчит только туннель Cloudflare, проксирующий трафик к `vps-api`.

## 4. Базы Данных: Разделение SQLite (Конкурентность)

СУБД SQLite для обеспечения HFT-скорости разделена на **три физически разных файла** (в режиме WAL). Это предотвращает взаимные блокировки при записи в диск (поскольку SQLite блокирует весь файл целиком на запись):

1. **`vps-api.db`**: Содержит профили управления (`trading_profiles`), API-ключи, и кэш сервера (`server_cache` для публикации сводки спредов каждые 30 секунд).
2. **`paper-trader.db`**: Таблица `trades` только для виртуальных (бумажных) сделок. При агрессивном трейдинге не блокирует боевые базы.
3. **`real-trader.db`**: Таблица `trades` для реальных денег. Работает с параметром `PRAGMA synchronous = OFF` для максимальной скорости записи, чтобы не тормозить потоки `engine::real`.

## 5. Ключевые паттерны работы для Агента:

1. **UI / Фронтенд (Отображение данных, Графики)**: Все файлы лежат в директории `public/`.
2. **Cloudflare Routing & Auth**: Вся логика моста находится в `src/index.js`.
3. **REST API / CRUD Операции со стейтами**: Логика обновления/получения данных для UI находится в директории `vps-api/`.
4. **Математическая / Торговая логика**: Все, что касается вычисления спредов, коннекта по WebSocket к биржам, отправки реальных ордеров (HMAC подписи, `RateLimits`, `tokio::join!`), и закрытия виртуальных/реальных сделок, находится внутри `core-node/src/`. 
   - Вычисления -> `spreads.rs`, `engine/paper.rs`, `engine/real.rs`
   - Коннекты -> `collector/[exchange].rs`
5. В `core-node` **НЕЛЬЗЯ** использовать блокирующие синхронные операции или писать тяжеловесную логику в горячем (Hot Path) цикле приема WebSocket сообщений. Обязательно применение `tokio::spawn` и использование фоновых процессов.
