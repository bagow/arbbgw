# Execution Engine (core-node/src/engine/cycle.rs)

## Механика Исполнения
Файл `cycle.rs` является сердцем системы. Он исполняет 1 цикл проверки стейта (Prices) против базы данных.

### Жизненный Цикл Сделки
1. **Балансы и Лимиты**: Проверяется по `EngineContext`. Если балансов нет — сделка скипается.
2. **Параллельное Исполнение**: `place_order` вызывается одновременно для `Leg A` и `Leg B` используя `tokio::join!`.
3. **Строгая Верификация**: Используется `fetch_order` для подтверждения, что IOC ордер действительно исполнился. *Никогда* не полагаться на локальный стакан вебсокета для подтверждения филлов. Учитывается поле `actual_vol_phys` (реальный налитый объем монет).
4. **Trimming (Срезание дельты)**: Если объемы не совпали (на Бинансе купилось 10 монет, на Гейте продалось 7) — движок немедленно и по рынку (Market) "сбрасывает" лишние 3 монеты на Бинансе с помощью `trim_position`. Убыток от тримминга идет в кастомный slippage.
5. **Fallbacks закрытия**: Если при закрытии (TakeProfit) биржа отвечает ошибкой или таймаутом, срабатывают защитные механизмы в коннекторах, а не в самом `cycle.rs`. `cycle.rs` может вызвать повтор после `close_verify_delay`, но конкретные хаки (типа "если маркет закрытие запрещено, кинь лимит на 5% глубже") делает коннектор.

## Избегание Phantom Trades
В БД `real-trader.db` сделка записывается *только* если обе стороны гарантированно подтвердили физическое исполнение (`phys_a > 0.0 && phys_b > 0.0`). Никакие "мертвые" или отмененные IOC ордера в БД не попадают.

## Передача таймаутов
Система использует динамические таймауты: параметр `api_timeout_ms` (из `TechnicalSettings`) пробрасывается из `settings` в `run_cycle`, откуда передается аргументом в методы трейта `ExchangeConnector` (`place_order`, `close_position`, `trim_position`). Библиотека `reqwest` использует этот таймаут для прерывания зависших соединений.
