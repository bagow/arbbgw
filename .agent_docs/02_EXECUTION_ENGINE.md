# Механика Торгового Исполнения (Execution Engine & Scanning)

Вся арбитражная бизнес-логика сконцентрирована в `core-node/src/engine/`. Этот слой системы оперирует абстракциями (`ExchangeConnector`) и чистой математикой.

## 🧠 Сканер Спредов и EMA Фильтрация
Перед тем как сделка попадает в цикл, она проходит через фильтр в `scanner.rs`.
1. **Экспоненциальная Справедливость (EMA Mid-Price)**: Скользящая средняя (EMA) базируется исключительно на *справедливой середине* (Mid-Price). 
2. **Истинная маржинальная девиация**: Сканер вычитает из рыночного спреда историческую норму `EMA Mid Deviation`. Если `structural_deviation` превышает `min_entry_spread`, сигнал передается в цикл.

## ⚙️ Жизненный Цикл Сделки (Engine Orchestration)

Архитектура двигателя построена на чистом разделении обязанностей (SOLID). Центральным оркестратором выступает файл `cycle.rs`, который просто последовательно вызывает специализированные менеджеры:

### 1. Risk Manager (`risk_manager.rs`)
До старта любых сделок `risk_manager` проверяет "здоровье" системы:
- **Margin & Balances**: Проверяет, хватает ли маржи в `e_ctx`. Позволяет избежать одноногих входов. Удерживает маржу при входе (`deduct_cached_balance`).
- **Global Exchange Bans**: Проверяет, не забанена ли биржа из-за таймаутов, технических работ или критических RTT-задержек.

### 2. Entry Manager (`entry_manager.rs`)
Обрабатывает открытие новых сделок (логика перенесена из старого монолитного cycle):
- **JIT VWAP Verification**: Перед выстрелом скачивает "тяжелые" стаканы `L2/L3` через REST API. Симулирует поглощение стакана на требуемый объем. Если реальный **VWAP-спред** меньше лимита, сделка отбраковывается как "Мираж".
- **Последовательный Выстрел (Sequential Execution)**:
  1. Высчитывается "Худая нога" (Thinner Leg).
  2. Худая нога отправляется **первой** (через IOC-лимит).
  3. "Толстая нога" отправляется **строго на тот объем**, который физически был исполнен на худой ноге.
- Замеряет миллисекундный пинг. При RTT > 500ms применяет страйки, которые при достижении лимита блокируют биржу в `risk_manager`.

### 3. Exit Manager (`exit_manager.rs`)
Обрабатывает закрытие открытых позиций:
- Проверяет актуальные ордербуки для открытых сделок.
- При достижении `Take-Profit` (или если спред закрытия `<= 0`) проводит JIT VWAP верификацию перед маркет-выходом.
- Если биржа отбраковала ордер, переводит сделку в персистентное состояние `CLOSING`.
- **Trimming**: Если из-за IOC остался перекос объемов, сбрасывает разницу по маркету (`trim_position`), сохраняя убыток в `slippage_cost`.

### 4. PnL Calculator (`pnl.rs`)
Чистые математические функции, не имеющие side-effects. Вычисляют текущий PnL и финансирование (Funding Cost). 
⚠️ **ПРАВИЛО**: Физический объем монет рассчитывается ТОЛЬКО как `volume / entry_price_a`. **ЗАПРЕЩАЕТСЯ** использовать цену `b` для расчетов ноги B, чтобы не создать иллюзию перекоса объемов.

---

## 🧮 Каноническая формула net PnL (active + history)
Для консистентности всех таблиц/графиков используется единая формула:
`net = gross - commission - funding - slippage`
Где `gross` это сумма по ногам (`pnl_a + pnl_b`), а не итог после комиссий. В history и stats запрещено иметь отдельные "особые" формулы, отличные от канонической.

## 🛡️ Параноидальные системы защиты депозита
1. Подсчитываются **Consecutive Failures** (5 подряд неудачных IOC). В случае превышения лимитов `EngineContext.is_killed` переходит в `true`.
2. Подсчитываются **Consecutive Trims** (3 подряд слитых по рынку 100% асимметричных разрывов). Ликвидирует ситуации, когда API биржи тотально глючит.
3. Фоновый процесс `position_sync` (описан в `04_WORKERS_AND_DB.md`) гарантирует, что сделки без позиций ликвидируются из БД.
