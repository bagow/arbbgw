# Архитектура и Главные Правила (System Architecture & Core Rules)

## Самое главное правило (CRITICAL RULE)
🚨 **СТРОГОЕ АРХИТЕКТУРНОЕ ПРАВИЛО [ОБЯЗАТЕЛЬНО К ИСПОЛНЕНИЮ]** 🚨
Никакая логика взаимодействия с биржами (обход багов, костыли для Hedge Mode, расчет fallback-цен для маркет-ордеров) **НЕ ДОЛЖНА ВЫНОСИТЬСЯ ИЗ КОННЕКТОРОВ** (`gate.rs`, `binance.rs` и т.д.) в общие движки вроде `cycle.rs`. Если какому-то коннектору требуются особые хаки для выполнения приказа (например, подмена price=0.0 на агрессивный лимитный ордер), **все делается строго внутри файла этого коннектора**. `cycle.rs` не должен "знать" о проблемах конкретных бирж. Он собирает чистую математику сканера и передает абстрактные команды коннекторам.

## Микросервисы

1. **`core-node` (Торговый движок)**
   - Процесс-монолит, читает вебсокеты, считает спреды, торгует.
   - Базы данных: Читает настройки из `vps-api.db`, пишет трейды в `real-trader.db`.
   - Вся логика в памяти: `state::EngineContext` хранит тики, балансы, спам-кулдауны.

2. **`vps-api` (Бэкенд Интерфейса)**
   - Веб-сервер Axum. Обслуживает браузерный UI. 
   - Сохраняет настройки в `vps-api.db`. Читает трейды из `real-trader.db`.

3. **Cloudflare Edge**
   - React UI раздается с Cloudflare Workers/Pages. `cloudflared` туннель пробрасывает порт 4000 от `vps-api`.

## Trade Lifecycle
1. Установлены настройки через UI.
2. WebSockets (`core-node/src/collector/`) обновляют `PriceMap`.
3. `core-node/src/engine/cycle.rs` пересчитывает спреды.
4. Вызов `place_order` параллельно на двух `ExchangeConnector`.
5. Строгая проверка `fetch_order` для подтверждения.
6. Вызов `trim_position` если нога асимметричная (потери идут в slippage).
7. Запись результата в `real-trader.db` через `TradeRepository`.
