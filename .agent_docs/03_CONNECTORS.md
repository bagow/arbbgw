# Коннекторы и Взаимодействие с Биржами (Exchange Connectors)

Все взаимодействие с криптобиржами изолировано в коннекторах. Оркестратор (`engine/`) не знает ни о форматах подписи (HMAC, RSA), ни о структуре JSON-ответов бирж.

> [!CAUTION]
> 🚨 **ЗАПРЕТ REST API [ОБЯЗАТЕЛЬНО К ИСПОЛНЕНИЮ]** 🚨
> **REST API (`http.get()`, `http.post()` к API бирж) СТРОГО ЗАПРЕЩЁН.**
> Все операции (ордера, проверка заливки, закрытие позиций, баланс, позиции, ордербуки) должны выполняться **ИСКЛЮЧИТЕЛЬНО через WebSocket**.
> REST блокируется Cloudflare, создаёт задержку 50-200мс, вызывает рейт-лимиты, и является **единственной причиной** "one-legged" сделок.

## 🔌 Архитектура Коннектора (`ExchangeConnector` trait)

Любая биржа имплементирует единый трейт `ExchangeConnector` (находится в `core-node/src/engine/exchanges/traits.rs`). 

Трейт обязывает реализовать абстракции:
1. `name()` — возвращает идентификатор (например `"gate"`).
2. `place_order(...)` — Размещает лимитные/маркет ордера строго через WebSocket. Возвращает стандартизированный `(Option<String>, f64, f64)` (Order ID, Inlined Fill Price, Inlined Fee).
3. `close_position(...)` — Сложная функция, отвечающая за надежное закрытие позиции. Разрешено (и нужно) использовать внутренний Retry Loop (Fallbacks), если биржа выдает сетевые ошибки.
4. `trim_position(...)` — Сверхбыстрый сброс (Dump) по маркету для ликвидации асимметрии объема ног.
5. `fetch_order(...)` — Опрос истории ордера для верификации IOC.
6. `fetch_positions(...)` — Получение открытых позиций аккаунта (Ghost trade prevention). Возвращает наш внутренний тип `PositionInfo`.
7. `fetch_orderbook(...)` — JIT запрос L2 стакана для VWAP верификации.

### 🛡️ Инкапсуляция костылей
Главное правило: **Все хаки и баги биржи чинятся только внутри коннекторов**. 
- Пример: API биржи `KuCoin` требует `&multiplier` равный лотам (size / lot_size).
- Вы не должны менять `entry_manager.rs`, чтобы научить систему понимать разницу лотов Kucoin. Вся конвертация происходит внутри реализации в `kucoin.rs`. 
- Обработка Rate limits и специфичных HTTP/WS кодов ошибок (например, Kucoin `429000`) происходит внутри коннектора.

### Close Verification Truthfulness (Критическое правило)
- `close_position()` НЕ имеет права возвращать успешный `CloseReceipt`, если цена/комиссия закрытия не подтверждены через `fetch_order`.
- Если по deep-verify видно, что позиция исчезла, но fill details не получены, коннектор обязан вернуть ошибку верификации (`unverified close`) вместо фиктивного `final_price=target_price` и `fee=0`.
- Это защищает PnL от скрытого искажения в таблице `trades`.

## ⚡ WebSocket Trading API (`core-node/src/engine/exchanges/ws_*.rs`)

Для минимизации задержки при размещении ордеров (2-8ms вместо 50-120ms REST), коннекторы поддерживают persistent WebSocket соединения.

### Архитектура WS Trading
1. **Lazy Init**: WS соединение создаётся при первом ордере через `get_or_init_*_ws()`. Используется `OnceLock` для singleton-инициализации.
2. **Persistent Connection**: Одно WS соединение переиспользуется. Auto-reconnect при обрыве (бесконечный loop с задержкой).
3. **WS-ONLY (NO REST FALLBACK)**: Если WS недоступен или вернул ошибку → ордер считается неисполненным (fail-fast). 
4. **Auth и Signature**: Выполняются строго в коннекторе (например, HMAC-SHA256). Менеджеры оркестратора не имеют дела с криптографией.

Вся WS-специфичная логика находится **строго внутри** файлов `ws_*.rs` и соответствующих коннекторов (`binance.rs`, `gate.rs`). Оркестратор `engine/` **не знает** о том, какой транспорт используется.
