## Исправления

1. **Комиссии каждого ордера.** Раньше `max(известные комиссии, общий резерв)` мог поглотить резерв неизвестной комиссии. При известных 0.30 USDT на первой ноге и ожидаемых 0.10 USDT на второй вычиталось 0.30 вместо 0.40. Теперь резерв добавляется отдельно по фактически исполненному объёму; нулевые подтверждённые комиссии и rebates сохраняются.
2. **Лимит TP покрывает глубину.** Средняя цена больше не используется как лимит закрывающего IOC. Лимит достигает последнего нужного уровня; TP проверяется по худшим ценам обеих ног с резервом комиссий. Текущая оценка и trailing stop используют VWAP. Изменение стакана между запросами всё ещё может вызвать частичное и аварийное закрытие.
3. **Счётчик рискованных выходов.** Успешный вход больше не обнуляет счётчик: исполнение не доказывает прибыль. Счётчик пока процессный и сбрасывается при перезапуске; это не денежный лимит просадки.
4. **Сверенная статистика.** PnL, wins/losses, средний результат, рейтинги и график используют закрытые `VERIFIED` записи с известным PnL. Добавлены breakeven и profit factor. График содержит последние 1000 результатов в хронологическом порядке. SQL-запросы статистики читают один согласованный снимок.
5. **Неизвестный PnL.** API истории сохраняет неизвестный net PnL вместо подстановки нулей за неизвестные расходы и вычисления выдуманного итога.
6. **Настройки SQLite.** Чтение по именам колонок устраняет зависимость от различающегося порядка колонок на свежей базе и после миграций. Иначе API мог показывать неверные плечо, глубину и время удержания.
7. **Доступ к профилям.** `/api/trading/settings/all` требует авторизации; он и `/api/profiles/:id` учитывают владельца. Общий `real-default` остаётся доступным обоим предусмотренным пользователям.

## Проверки

Локально проверен разбор всех 63 Rust-файлов без сборки, синтаксис JavaScript и `git diff --check`. Шесть Python-тестов проходят. Они проверяют неизвестные результаты, большинство побед при общем убытке, чтение SQLite без записи и некорректные стаканы.

GitHub Actions для `7b523a6` выполнил `cargo check --workspace`, 58 Rust-тестов и release-сборку. Последующие изменения TP и истории добавляют регрессии. Итоги каждой сборки сохраняются в `ci-results/<полный SHA>-<run>-<attempt>`; перед публикацией нужен результат именно текущего SHA. Rust локально и на VPS не собирался, согласно README.

```sh
python3 scripts/audit_performance.py /path/to/real-trader.db --profile real-default
python3 -B -m unittest discover -s scripts -p 'test_*.py'
```

`scripts/server_audit.py` проверяет production-пути только для чтения. Workflow `audit.yml` сохраняет JSON в artifact и служебную ветку. Скрипт не читает ключи или окружение сервисов и не обращается к торговым API.

Дополнительно настроен запуск release-бинарника на сервере в отдельном временном каталоге. Профили копируются через SQLite backup API и выключаются только в копии; торговая база создаётся пустой. Окружение задаётся явным списком без биржевых ключей, пустой `.env` предотвращает поиск родительских файлов. Сборщики выключены; проверяются `/health`, SHA и отсутствие ордеров/сделок. Процесс затем завершается, временные файлы удаляются. Результат сохраняется в `smoke-results/<SHA>-<run>`. Это проверка запуска, а не испытание доходности или замена production-сервиса. `CORE_DIAGNOSTIC_PATH` позволяет избежать перезаписи общего диагностического файла при таком запуске.

## Область проверки и оставшиеся ограничения

Проверены связи сканера, спецификаций, маржи, журнала, исполнения, надзора, финансовой сверки, сборщиков Binance/Gate/KuCoin, API, UI и CI. Для остальных адаптеров проверено ограничение входа через `supports_managed_orders`; старые методы остаются в коде. Синтаксическая проверка всех файлов не равна построчной верификации всех биржевых протоколов.

Остаются нестабильный канал Binance, неполные данные replay, несверенная история, отсутствие денежного лимита общей просадки, кеш комиссий без регулярного обновления и повторная простановка timestamps кеша счетов. Время публикации кеша не доказывает свежесть биржевого ответа. Изоляция общей истории по владельцам требует отдельного решения: экран показывает сделки одного общего торгового счёта.

Версия подготовлена для дальнейшего контролируемого испытания. Production-деплой и запуск реальной торговли в рамках аудита не выполнены. Положительное математическое ожидание не установлено.
