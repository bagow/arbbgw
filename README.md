# CEX Arbitrage Trading Engine - Текущая Архитектура

Это актуальное описание архитектуры на момент текущих правок (Апрель 2026), где мы объединили и упорядочили работу баз данных и микросервисов.

## 🏗️ Микросервисы (VPS)

1. **`core-node` (Торговый движок)**
   - **Роль**: Единый монолитный процесс, который круглосуточно качает WebSocket потоки ордербуков (Gate, HTX, Binance и др), вычисляет спреды и открывает/закрывает сделки (как paper_trader, так и real_trader).
   - **Фокус**: Не имеет UI, работает в фоне как systemd-сервис (`core-node.service`).
   - **Базы данных**:
     - Читает *настройки* (TradingProfiles) из `vps-api.db`
     - Сохраняет *сделки* (Trades), кэш бирж, ордера в `paper-trader.db` / `real-trader.db`
     - Сохраняет *кэш списков пар* (server_cache) в `paper-trader.db`

2. **`vps-api` (Бэкенд Интерфейса)**
   - **Роль**: Веб-сервер на Rust (Axum), связующее звено между базой данных и браузерным UI пользователя.
   - **Фокус**: Отдает JSON для Дашборда, отвечает за сохранение настроек профилей (Settings Dashboard) и отдачу истории торгов. Не вычисляет спреды, ничего сам не покупает.
   - **Базы данных**:
     - Читает/пишет *настройки профилей* напрямую в `vps-api.db`
     - Читает *историю торгов* и *активные сделки* из `paper-trader.db` / `real-trader.db`
     - Вытягивает закэшированные *списки пар торгуемых бирж* из `paper-trader.db` (server_cache)

3. **Cloudflare Tunnel (`cloudflared`)**
   - Проксирует запросы от публичного домена `arb.bagow.com` напрямую в локальный порт `vps-api`, который слушает на 4000 порту.

## 🗄️ Базы данных (SQLite)

На данный момент система строго разделена на три файла базы данных, чтобы настройки (UI) и транзакции (Trade Engine) не блокировали друг друга и не перезаписывались:

| Имя Файла | Роль | Владелец Записи (кто пишет) | Владелец Чтения (кто читает) |
| --- | --- | --- | --- |
| `vps-api.db` | Хранит настройки профилей (`trading_profiles`), включенные биржи, лимиты и объемы (`0.5%`, `$10`), пароли юзеров. | `vps-api` (сохраняет настройки с UI) | `core-node` (читает перед каждой сделкой) |
| `paper-trader.db` | Хранит бумажные сделки (Trades), PnL, и закэшированную аналитику рынка (`server_cache`). | `core-node` (пишет сделки и кэш пар) | `vps-api` (читает для UI дашбордов) |
| `real-trader.db` | Хранит реальные сделки с ордерами и PnL. Полная копия структуры paper-базы для боевого режима. | `core-node` (реал. движок) | `vps-api` (читает для интерфейса) |

## 🔗 Жизненный цикл типичного запроса

1. **Сохранение настроек**: Пользователь меняет "Slippage 0.5" -> Браузер шлет PATCH-запрос в Cloudflare -> `vps-api` перезаписывает строку в `vps-api.db`.
2. **Открытие сделки**: `core-node` видит спред в WebSocket. Он запрашивает последние настройки из `vps-api.db`. Если спред подходит под сохраненные лимиты, он вычисляет размер комиссии и открывает лонг/шорт.
3. **Запись в UI**: `core-node` вносит транзакцию об открытии лонга со статусом OPEN прямо в `paper-trader.db`. Буквально через секунду `vps-api` вычитывает её оттуда и пользователь видит её в "Active Trades" без перезагрузок.

---
*Сконфигурировано так, чтобы торговый цикл core-node никогда не падал при пиковых нагрузках фронтенда или частых сохранениях интерфейса.*

## ⚙️ Внутренняя Архитектура `core-node` (Trading Engine)

В апреле 2026 года движок прошел этап "paranoid-level refactoring", чтобы навсегда исключить `panic!` из-за гонок данных, грязи сырых SQL-запросов и глобального мутабельного стейта, при этом СОХРАНИВ молниеносную скорость монолита.

### Почему движок остался таким же молниеносным? ⚡
Несмотря на красивое разделение логики, **скорость работы не пострадала ни на миллисекунду**. 
Все рыночные котировки, стаканы (OrderBooks), комиссии, балансы, лимиты, тики и блокировки спама (Cooldowns) ПО-ПРЕЖНЕМУ хранятся **исключительно в оперативной памяти** благодаря `state::EngineContext`.
База данных (SQLite) используется асинхронно (`tokio_rusqlite` кидает запросы в отдельный фоновый пул потоков) или через `tokio::spawn`. Это значит, что пока БД медленно сохраняет запись о трейде на SSD, торговый loop уже летит дальше открывать следующие сделки без малейшей блокировки!

1. **`EngineContext` (Память)**
   - Весь горячий стейт (Tick Sizes, Balances, Multipliers, Cooldowns) загружается при старте и живет в памяти через сверхбыстрые потокобезопасные `DashMap` внутри `Arc<EngineContext>`.

2. **`ExchangeConnector` (Абстракция Бирж)**
   - Трейт `ExchangeConnector` стандартизует работу: `place_order`, `close_order`, `fetch_order`.
   - Больше никакого "лапша-кода" из `match exchange` на сотни строк. Добавление новой биржи теперь требует просто написать отдельный файл под трейт. Управление API остается строго изолированным.

3. **Слой `run_cycle` (Мейнлуп Трейдинга)**
   - Гигантская функция `run_cycle` (бывшая в `real.rs`) полностью декомпозирована в модуль `cycle.rs`.
   - Цикл разбит на логические фазы: `process_closes` (закрытия), `evaluate_entry` (проверка входов) и `execute_legs` (исполнение ног).
   - Ликвидированы проблемы с параллельными `await`, а временные указатели грамотно живут в памяти избегая `E0716`.

4. **`db.rs` / `TradeRepository` (Абстракция БД)**
   - Все сырые строки SQL-запросов (типа `INSERT INTO trades`, `UPDATE trades`) навсегда выброшены из торгового алгоритма!
   - Теперь `run_cycle` просто вызывает `repo.mark_trade_closed(...)` или `repo.insert_new_entry(...)`. 
   - Это гарантирует, что бизнес-логика торговца никогда больше не сломается от того, что где-то забыли закрывающую кавычку или перепутали колонку БД.
