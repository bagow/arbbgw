# CEX Arbitrage Trading Engine - Текущая Архитектура

> [!CAUTION]
> 🚨 **СТРОГОЕ АРХИТЕКТУРНОЕ ПРАВИЛО [ОБЯЗАТЕЛЬНО К ИСПОЛНЕНИЮ]** 🚨
> Никакая логика взаимодействия с биржами (обход багов, костыли для Hedge Mode, расчет fallback-цен для маркет-ордеров) **НЕ ДОЛЖНА ВЫНОСИТЬСЯ ИЗ КОННЕКТОРОВ** (`gate.rs`, `binance.rs` и т.д.) в общие движки вроде `cycle.rs`. Если какому-то коннектору требуются особые хаки для выполнения приказа (например, подмена price=0.0 на агрессивный лимитный ордер), **все делается строго внутри файла этого коннектора**. `cycle.rs` не должен "знать" о проблемах конкретных бирж. Он собирает чистую математику сканера и передает абстрактные команды коннекторам.

Это актуальное описание архитектуры на момент текущих правок (Апрель 2026), где мы объединили и упорядочили работу баз данных и микросервисов.
## 🏗️ Микросервисы (VPS)

1. **`core-node` (Торговый движок)**
   - **Роль**: Единый монолитный процесс, который круглосуточно качает WebSocket потоки ордербуков (Gate, HTX, Binance и др), вычисляет спреды и открывает/закрывает сделки.
   - **Фокус**: Не имеет UI, работает в фоне как systemd-сервис (`core-node.service`).
   - **Базы данных**:
     - Читает *настройки* (TradingProfiles) из `vps-api.db`
     - Сохраняет *сделки* (Trades), кэш бирж, ордера в `real-trader.db`
     - Сохраняет *кэш списков пар* (server_cache) в `real-trader.db`

2. **`vps-api` (Бэкенд Интерфейса)**
   - **Роль**: Веб-сервер на Rust (Axum), связующее звено между базой данных и браузерным UI пользователя.
   - **Фокус**: Отдает JSON для Дашборда, отвечает за сохранение настроек профилей (Settings Dashboard) и отдачу истории торгов. Не вычисляет спреды, ничего сам не покупает.
   - **Базы данных**:
     - Читает/пишет *настройки профилей* напрямую в `vps-api.db`
     - Читает *историю торгов* и *активные сделки* из `real-trader.db`
     - Вытягивает закэшированные *списки пар торгуемых бирж* из `real-trader.db` (server_cache)

## 🌐 Cloudflare Edge (Фронтенд и Роутинг)

1. **Cloudflare Frontend (React/Vite Worker)**
   - Красивый и современный интерфейс Дашборда целиком хостится и раздается глобальной сетью Cloudflare (Workers/Pages).
   - Это дает моментальную загрузку UI из любой точки мира и **нулевую нагрузку** на наш рабочий VPS для отдачи статики.
   - Браузер скачивает UI с Edge-серверов Cloudflare, а затем React-приложение незаметно связывается с нашим торговым VPS для получения данных о сделках.

2. **Cloudflare Tunnel (`cloudflared`)**
   - Безопасно проксирует запросы от публичного домена `arb.bagow.com` напрямую в локальный защищенный порт `vps-api` (порт 4000).
   - Позволяет вообще не открывать внешние порты (80/443) на VPS. Торговый сервер полностью спрятан за защитой Cloudflare.
## 🗄️ Базы данных (SQLite)

На данный момент система строго разделена на три файла базы данных, чтобы настройки (UI) и транзакции (Trade Engine) не блокировали друг друга и не перезаписывались:

| Имя Файла | Роль | Владелец Записи (кто пишет) | Владелец Чтения (кто читает) |
| --- | --- | --- | --- |
| `vps-api.db` | Хранит настройки профилей (`trading_profiles`), включенные биржи, лимиты и объемы (`0.5%`, `$10`), пароли юзеров. | `vps-api` (сохраняет настройки с UI) | `core-node` (читает перед каждой сделкой) |
| `real-trader.db` | Хранит сделки с ордерами, PnL и кэшированную аналитику рынка (`server_cache`). | `core-node` | `vps-api` (читает для интерфейса) |

## 🔗 Жизненный цикл типичного запроса

1. **Сохранение настроек**: Пользователь меняет "Slippage 0.5" -> Браузер шлет PATCH-запрос в Cloudflare -> `vps-api` перезаписывает строку в `vps-api.db`.
2. **Открытие сделки**: `core-node` видит спред в WebSocket. Он запрашивает последние настройки из `vps-api.db`. Если спред подходит под сохраненные лимиты, он вычисляет размер комиссии и открывает лонг/шорт.
3. **Запись в UI**: `core-node` вносит транзакцию об открытии лонга со статусом OPEN прямо в `real-trader.db`. Буквально через секунду `vps-api` вычитывает её оттуда и пользователь видит её в "Active Trades" без перезагрузок.

---
*Сконфигурировано так, чтобы торговый цикл core-node никогда не падал при пиковых нагрузках фронтенда или частых сохранениях интерфейса.*
