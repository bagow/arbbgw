# Real Trader HFT: Однопроцессная Архитектура и План Реализации

Этот документ описывает новую ультимативную архитектуру платформы, переработанную для достижения сверхнизких (HFT) задержек, безопасности боевых депозитов и чистоты кодовой базы.

---

## 1. Архитектурное Видение: Single-Process Core (Zero-Latency)

Чтобы исключить любые затраты времени на передачу огромных JSON-пакетов по HTTP между микросервисами (что сейчас съедает от 2 до 5 миллисекунд), мы объединяем компоненты сбора и исполнения. 

**Анализ текущей архитектуры (Bottleneck):**
`rust-collector` (находит спред) -> Сериализация в JSON (50 МБ) -> TCP/HTTP POST на `localhost` -> `real-trader` -> Десериализация -> Отправка на биржу.

**Новая архитектура (Zero-Latency Core):**
`rust-collector` и `real-trader` будут скомпилированы в **один высокопроизводительный бинарник (`core-node`)**. Однако их код не превратится в "кашу" — логика будет строго разделена по модулям (обособленным Rust-папкам внутри проекта). Передача спреда будет происходить по **In-Memory структуре данных** в виде прямых ссылок в оперативной памяти (задержка ~100 наносекунд). Наружу (для UI и `paper-trader`) этот бинарник продолжит отдавать привычный JSON.

> **Важно по типу канала**: Использовать `tokio::sync::broadcast` — неправильно. В `broadcast`-канале, если потребитель (engine) не успевает читать, старые сообщения **бесследно теряются** (`Lagged` ошибка). Правильный паттерн, который уже используется в `rust-collector` и должен быть перенесён в `core-node`: `Arc<DashMap<String, TickerData>>` + `Arc<Notify>`. Collector пишет свежие данные напрямую в DashMap, затем стреляет `Notify::notify_one()`. Engine просыпается, читает свежайшие данные из той же DashMap сразу без копирования. Никаких потерь, никаких очередей.

### Структура модулей нового бинарника (`core-node`):
- `src/collector/` — логика подключения к WS бирж, сбор стаканов и поиск спредов.
- `src/engine/` — чистая математика `real-trader` и `paper-trader` (алгоритм принятия решений, Smart Volume, расчет риск-лимитов).
- `src/exchange/` — модуль коннекторов бирж (API клиент).
- `src/api/` — **(Бывший `vps-api`)** веб-сервер на базе Axum, общающийся с дашбордом `trading.js`. Работает на порту `4000` и обслуживает запросы фронтенда.

## 2. Модуль Коннекторов (Exchange Client Library)

Грязная работа с HTTP-запросами, HMAC-подписями и WebSocket-потоками бирж будет полностью изолирована. Движок торговли (`engine`) не должен знать, как именно хешируется строка для KuCoin или Gate.

### 2.1 Unified Trait
В модуле `exchange` будет создан единый интерфейс (Rust Trait), который реализуют все биржи:
```rust
#[async_trait]
pub trait ExchangeClient {
    async fn place_order(&self, pair: &str, side: Side, size: f64, order_type: OrderType) -> Result<OrderResult>;
    async fn close_position(&self, pair: &str, size: f64) -> Result<String>; // возвращает order_id закрывающего ордера
    async fn get_margin_balance(&self) -> f64;
    /// Проверка реально исполненного объёма по order_id (для Partial Fill Sync).
    /// Возвращает (filled_qty_in_usd, status: "FILLED"|"PARTIAL"|"CANCELLED")
    async fn get_order_fill(&self, order_id: &str, pair: &str) -> Result<(f64, String)>;
}
```

### 2.2 Сетевая оптимизация пулов (TCP Keep-Alive)
Для модулей API клиентов мы настроим пул `reqwest::ClientBuilder` на агрессивное удержание открытых каналов связи с серверами бирж (Persistent Connections). Это избавит нас от необходимости делать 100-миллисекундный процесс TLS-рукопожатия (Handshake) при каждом броске ордера.

## 3. Модуль Исполнения: Concurrent Firing и Leg Risk

Модуль `engine` слушает канал в памяти и мгновенно активирует протокол входа:

**Шаг 1. Pre-trade Guard & Margin Check**
Быстрая проверка по настроенным `min_entry_spread` для профиля. Запрос в кэш свободной маржи `Available USDT`, чтобы не ловить отказы при недостатке средств.

**Шаг 2. Smart Volume Sizing**
Бот рассчитывает объем исходя из реальной плотности стакана:
`Trade_Volume = MIN(Settings.trade_volume, data_a.vol, data_b.vol)`.

**Шаг 3. Concurrent Firing (Только `tokio::join!`)**
Отправка ордеров (через `ExchangeClient` интерфейс) на биржи А и Б происходит абсолютно одновременно. Ожидание ответа через `tokio::join!(future_a, future_b)`.

**Шаг 4. Управление Рисками (Leg Risk Fallback)**
Самый критически важный узел для боевой торговли. Результат параллельной отправки обрабатывается жестко:
- **Успех**: Обе ноги (Legs) вернули `FILLED`.
- **Отказ**: Обе ноги отвергнуты. Игнорируем.
- **Одноногая уязвимость (Leg Asymmetry)**: Биржа `А` исполнила ордер, а `Б` вернула `HTTP 400` / `Rate Limit` / Упала сеть.
  - **Fallback Task**: Модуль `engine` мгновенно создает задачу спасения ("panic task"). Он вызывает `exchange.close_position(...)` для биржи `А`. Цель — закрыть актив в ту же секунду рыночным ордером, потеряв лишь копейки на комиссии тейкера, и спасти депозит от падения открытой монеты. Эта задача оборачивается в цикл повторов `Exponential Backoff Retriever` на случай временной смерти API биржи.

**Шаг 5. Частичное исполнение (Partial Fills Sync)**
Поскольку мы бьем маркет-ордерами (или IOC), биржа может исполнить только часть (например $300 из запрошенных $1000). Алгоритм:
1. После `tokio::join!` вызываем `exchange.get_order_fill(order_id)` для каждой ноги (REST-запрос, ~50мс).
2. Сравниваем `filled_a` и `filled_b`.
3. Если разница > 1% — немедленно кроем рыночным ордером излишек бо́льшей ноги, сравнивая объёмы.
4. В БД записываем **реально исполненный** объём, а не запрошенный.

**Как получить filled объём на каждой бирже:**
- **Gate.io**: `GET /api/v4/futures/usdt/orders/{order_id}` → поле `size` (исполненное) vs `left` (остаток). Filled = `size - left`.
- **HTX**: `POST /linear-swap-api/v1/swap_order_info` body `{"order_id": ..., "contract_code": ...}` → поле `data.trade_volume`.
- **KuCoin**: `GET /api/v1/orders/{order-id}` → поле `data.dealSize` (количество контрактов).

## 4. Хранение Стейта, Баз Данных и Изоляция Ключей

### 4.1 "In-Memory" Торговля без блокировок диска
Торговый движок `engine` для боевых профилей **никогда** не должен обращаться к жесткому диску (HDD/SSD SQLite) на этапе выполнения `Hot Path` (принятия решения по спреду). SQLite-запросы слишком медленные для HFT.
- **Кэширование**: Биржевые API ключи загружаются из БД в оперативную память (`RwLock<HashMap>`) при старте или по кнопке. Все лимиты маржи и стейт-машина сделок также "живут" в ОЗУ.
- **Асинхронная запись**: Когда сделка успешно открыта или закрыта, данные о ней отправляются по фоновому каналу (background thread) воркеру записи в отдельную БД `real-trader.db` (с настроенными режимами высокоскоростной записи `WAL` и `PRAGMA synchronous = OFF`). Эта база не пересекается со сканером или `paper-trader`.

### 4.3 Разделение баз данных в `core-node` (три отдельных файла)

В `core-node` базы данных **остаются отдельными файлами** — объединять их в одну нет смысла. Причина: SQLite имеет один глобальный write-lock **на файл**. Если объединить всё, то запись сделки от paper-trader будет блокировать запись сделки от real-trader и обновление профиля через api — они будут ждать в очереди. В трёх отдельных файлах каждый пишет совершенно независимо.

**Распределение файлов в `core-node`:**

| Файл | Владелец (модуль) | Содержимое | SQLite режим |
|------|-------------------|------------|-------------|
| `vps-api.db` | `src/api/` | `trading_profiles`, `server_cache`, `exchange_keys` | `WAL`, `synchronous=NORMAL` |
| `paper-trader.db` | `src/engine/paper` | `trades` (paper) | `WAL`, `synchronous=NORMAL` |
| `real-trader.db` | `src/engine/real` | `trades` (real), только боевые сделки | `WAL`, `synchronous=OFF` (максимальная скорость) |

Каждый модуль получает свой `Arc<Connection>` при старте. Никакой миграции не нужно — файлы те же, что были у старых сервисов, просто теперь открываются внутри одного процесса. Новая таблица `exchange_keys` добавляется в `vps-api.db` через стандартный `CREATE TABLE IF NOT EXISTS` при старте.


### 4.2 Слой управления: Интеграция `vps-api`
- Бывший автономный сервис `vps-api` теперь **становится модулем `api`** внутри нашего `core-node`. Он продолжит слушать порт `4000` и обслуживать запросы вашего Frontend-дашборда из Cloudflare.
- **Интеграция с движками**: Теперь, когда вы нажимаете "Сохранить настройки профиля", веб-сервер не просто пишет их в SQLite. Он напрямую обращается к общей оперативной памяти (`Arc<RwLock<GameState>>`) и мгновенно (за `1` микросекунду) меняет настройки активных движков `rust-collector`, `real-trader` и `paper-trader`, без необходимости для движков опрашивать базу каждую секунду! 
- **Panic Button (Кнопка спасения)**: Нажав кнопку "Close All" в UI, `vps-api` просто активирует Panic-метод внутри того же процесса программы, мгновенно вызывая Market-Close у Торгового Движка.
- **Безопасность API-Ключей**: Структура `TradingProfile` получит скрытые поля `{gate_key, htx_secret}` и т.д. В базу они пишутся зашифрованно, а при старте `core-node` загружаются в оперативную память профилей (для доступа `real-trader`). Глобальный `.env` для ключей больше не используется.

## 6. Инфраструктура: Миграция на сервер (Швейцария)

Для минимизации сетевых задержек бот будет перенесен на швейцарский сервер. 

**Креды:**
`ssh opc@140.238.217.190`

### 6.1 Правильная настройка Cloudflare Tunnel (Мост)
В прошлый раз могли возникать обрывы или ошибки 502/503 из-за отсутствия явных правил маршрутизации (Ingress Rules) или ручного запуска туннеля вместо фоновой службы (Systemd). 

**Шаги для 100% стабильного "моста":**

1. **Загрузка и логин**:
   ```bash
   curl -L --output cloudflared.deb https://github.com/cloudflare/cloudflared/releases/latest/download/cloudflared-linux-amd64.deb
   sudo dpkg -i cloudflared.deb
   cloudflared tunnel login
   ```
2. **Создание и роутинг туннеля**:
   ```bash
   cloudflared tunnel create cex-arb
   cloudflared tunnel route dns cex-arb api.arb.bagow.com
   ```
3. **Строгий конфиг (Критический шаг)**:
   Создаем `~/.cloudflared/config.yml` и явно прописываем `ingress`, чтобы туннель знал, на какой локальный порт слать трафик:
   ```yaml
   tunnel: <ВАШ-TUNNEL-ID>
   credentials-file: /home/opc/.cloudflared/<ВАШ-TUNNEL-ID>.json
   
   ingress:
     - hostname: api.arb.bagow.com
       service: http://localhost:8080 # Заменить на порт vps-api, если он другой
     - catch-all: http_status:404
   ```
4. **Установка в виде фоновой системной службы**:
   Это гарантирует, что мост поднимется автоматически при перезагрузке сервера и не умрет после закрытия SSH.
   ```bash
   sudo cloudflared service install ~/.cloudflared/config.yml
   sudo systemctl enable cloudflared
   sudo systemctl restart cloudflared
   ```

Эта настройка скроет IP `140.238.217.190` за мощным WAF от Cloudflare, защитив боевой швейцарский сервер от прямого DDoS.

## 7. Продвинутые HFT-оптимизации и скрытые риски (Рекомендации AI)

Проведя финальную оценку архитектуры высокочастотного арбитража, я выявил 5 неочевидных узких мест, которые мы должны учесть для максимальной выживаемости и скорости бота:

### 7.1 Смерть от рассинхронизации часов (NTP Drift)
- **Риск**: Алгоритмы подписи бирж (HMAC) зависят от точного времени. Если системные часы вашего швейцарского VPS "уплывут" (drift) даже на 1000 миллисекунд, биржи начнут отвергать ваши ордера с ошибкой `Timestamp outside of the recvWindow`.
- **Решение**: На новом сервере мы обязаны настроить жесткую синхронизацию времени через демона `chronyd` или `systemd-timesyncd`, опрашивающего стратум-сервера не раз в сутки, а каждую минуту.

### 7.2 Задержка на DNS-резолвинг (DNS Bottleneck)
- **Риск**: Прежде чем отправить пакет на `api.gateio.ws`, Linux делает запрос к DNS провайдеру, чтобы узнать IP (что занимает 10-30 мс). В Linux по умолчанию нет хорошего DNS-кэша.
- **Решение**: Встроить в `reqwest::Client` поддержку `trust-dns` (кэширование внутри Rust) ИЛИ установить на сервере локальный кэширующий резолвер `dnsmasq` / `systemd-resolved`. Это срежет задержку до 0 мс.

### 7.3 Привязка потоков к ядрам (CPU Affinity)
- **Риск**: Когда ОС переключает задачу (Context Switch) между ядрами процессора, теряется кэш L1/L2 процессора (штраф до 10-50 микросекунд).
- **Решение**: Самый горячий торговый поток (который принимает спреды и шлет ордера) можно "прибить" гвоздями к отдельному ядру процессора (`core_affinity`). Никакие другие процессы ОС не смогут прервать этот поток.

### 7.4 Мониторинг комиссий Funding (Фандинг) без задержек
- **Риск**: Делать REST-запрос к бирже, чтобы узнать текущий `Funding Rate` прямо перед сделкой — это самоубийство для скорости.
- **Решение**: Фоновая асинхронная задача должна раз в 1 минуту тихо опрашивать биржи и складывать `Funding Rates` в `RwLock` кэш оперативной памяти. Торговый движок берет эти цифры из кэша мгновенно, не ожидая сети.

### 7.5 Безопасность депозита (IP Whitelisting)
- **Риск**: Если злоумышленник сольет базу SQLite с вашими API-ключами.
- **Решение**: На стороне Gate.io, KuCoin, HTX ключи должны быть сгенерированы со строгой привязкой **только к швейцарскому IP** `140.238.217.190`. Даже если ключи украдут, хакер не сможет совершить ни одной сделки со своего компьютера.

### 7.6 Сломанный генератор дат в HTX-коннекторе (критический баг)
- **Риск**: Текущий `real-trader` содержит самодельную функцию `chrono_like_ts()`, которая считает все месяцы по 30 дней и игнорирует високосные годы. В результате уже в 2026 году она возвращает **неправильную дату на 2–3 дня**. HTX проверяет timestamp подписи и отклоняет ордера с ошибкой `Timestamp outside recvWindow`, если расхождение с реальным временем больше 60 секунд — а у нас расхождение в днях.
- **Решение**: В `core-node` добавить зависимость `chrono = { version = "0.4", features = ["clock"] }` и заменить функцию на одну строку:
  ```rust
  fn utc_ts() -> String {
      chrono::Utc::now().format("%Y-%m-%dT%H:%M:%S").to_string()
  }
  ```

### 7.7 Защита от Rate Limits бирж (Rate Limiter)
- **Риск**: Биржи имеют жёсткие лимиты на количество ордеров в секунду: Gate.io — 100 req/10s, KuCoin — 30 req/3s, HTX — 10 req/1s. Если несколько спредов появились одновременно и бот пытается открыть несколько сделок сразу — API вернёт `HTTP 429 Too Many Requests`. В этот момент одна нога может открыться, а вторая упасть из-за лимита. Это триггерит Leg Asymmetry даже при идеально написанном коде.
- **Решение**: В модуле `exchange` перед каждым `place_order` вызовом добавить `RateLimiter` per-exchange. Использовать крейт `governor` (token bucket алгоритм):
  ```rust
  // Пример для Gate.io: не более 8 ордеров в секунду
  let gate_limiter = Arc::new(RateLimiter::direct(Quota::per_second(nonzero!(8u32))));
  gate_limiter.until_ready().await; // блокирует асинхронно, не тратит CPU
  let result = gate_place_order(...).await;
  ```
  Лимитер живёт в `AppState` как `Arc<RateLimiter>` — один на весь процесс, не на запрос.

### 7.8 Проверка реального объёма заполнения после ордера (Partial Fill Guard)
- **Риск**: Маркет-ордера на малоликвидных парах могут исполниться лишь частично (например, биржа исполнила $300 из $1000). Если не проверить — бот запишет в БД `volume = 1000`, но реально держит позицию на `300`. Это сломает весь расчёт PnL, trailing stop и Leg Risk Fallback.
- **Решение**: В `core-node` после каждого `tokio::join!` открытия — делать дополнительный `tokio::join!` из двух `get_order_fill(order_id)` REST-запросов (реализован через трейт, см. секцию 2.1). Логика:
  1. Если оба `FILLED` и объёмы совпадают в пределах 1% — записываем в БД номинальный объём.
  2. Если объёмы расходятся — кроем маркет-ордером излишек большей ноги, в БД записываем `MIN(filled_a, filled_b)` как финальный объём.
  3. Если одна нога вернула `CANCELLED` — срабатывает стандартный Leg Risk Fallback (Шаг 4).
